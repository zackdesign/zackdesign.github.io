Zack Design has published **[mintosh](https://github.com/isaacrowntree/mintosh)**, a set of scripts that turns **Linux Mint Xfce** into a close copy of current macOS, the macOS 26/27 "Liquid Glass" look, in light, dark or automatic, on an old Mac that Apple no longer updates. It also covers the move itself: back up the Mac from a second Mac, sort the files, install Mint, then three scripts for the system, the look and the keyboard. It was built for one person: the owner of a 2013 MacBook Air (MacBookAir6,1, 4 GB of RAM) whose last macOS was Big Sur, and who should not have to learn anything new to keep using it.

This post walks through:

- what a theme gives you and what it doesn't;
- why nothing that macOS keeps running is allowed to stay running here;
- Mission Control as a 307-line Python program, and the two bugs that made it look broken;
- why Launchpad is two windows;
- three ways Xfce kept showing yesterday's appearance;
- a use-after-free in the global menu plugin that Ubuntu ships, and the 27-line patch script 4 now builds in;
- a compositor that aborts on its own internal check;
- what the tests prove, and why they stopped testing two upstream projects.

## A theme is the easy 20%

The look comes from people who have already done it well. [MacTahoe](https://github.com/vinceliuice/MacTahoe-gtk-theme) is a careful recreation of the macOS Tahoe theme, icons and cursors. [picom](https://github.com/yshui/picom) is the compositor that blurs what sits behind glass, [Toshy](https://github.com/RedBearAK/toshy) remaps the Mac keyboard, Plank is the dock, and Touchegg reads the trackpad gestures.

Install all of that and you have something that looks like a Mac in a screenshot and nothing like one in use. Most of mintosh is what sits between those projects:

- **The menu bar.** The Apple menu, then the active app's name in bold and *its* File, Edit and View menus, lifted out of the window by `xfce4-appmenu-plugin`. Status icons are in macOS's order, and the date reads the way macOS writes it ("Mon 26 Oct 9:41 AM"). There's no bar behind them: like Tahoe, the text sits on the wallpaper with a faint shade.
- **The Apple menu.** It's a real menu: About This Computer, System Settings, Appearance, App Store, Force Quit, Sleep, Restart, Shut Down, Lock Screen and Log Out, with separators where macOS puts them. It's Xfce's own applications menu pointed at a custom `.menu` file. The entries live outside the normal app folders, so they don't also turn up in search.
- **Keys and gestures.** ⌘C, ⌘V, ⌘Q, ⌘W and ⌘Tab. ⌘⇧3 saves "Screenshot 2026-10-26 at 09.41.12.png" to the Desktop with no Save dialog. (xfce4-screenshooter only saves silently when handed a full file name; give it a folder and it asks.) F3 and F4 do what's printed on them. Three fingers up opens Mission Control, three fingers sideways changes desktop, and a thumb-and-three-finger pinch opens Launchpad.
- **The 2013 hardware:**
  - the installer can't see the SSD without `intel_iommu=off`;
  - the desktop froze after about an hour until SATA link power saving was turned off, and kept off, because the battery saver TLP turns it back on;
  - Broadcom Wi-Fi and FaceTime camera drivers, and a fan controller;
  - battery warnings that use the menu bar's percentage, because the kernel's own figure reads lower on this Mac.

## 4 GB means nothing stays running

Chrome alone will fill 4 GB, so the rule was that anything macOS keeps resident exists here only while it's on screen.

Spotlight and Launchpad are [rofi](https://github.com/davatorium/rofi), a launcher that starts when called and exits when closed. I tried Ulauncher first, the usual Spotlight stand-in on Linux. It stays in memory at 100 MB or more, which on this machine is a browser tab.

Mission Control is `bin/mission-control`, 307 lines of Python and GTK 3. It reads the open windows through Wnck, the window-list library Xfce's own panel uses. It draws each preview from the compositor's copy of the window, so covered windows show too, and it exits when it closes. The Spaces bar runs across the top: click a desktop to go there, + to add one, ✕ to remove the last. Drag a preview onto a desktop to move that window.

![Mission Control: "Desktop 1" and + buttons across the top, and previews of a Finder window and a Text Editor window labelled with their app names, over the wallpaper.](/images/blog/mintosh-mission-control.jpg)

Two bugs in it are worth telling, because both looked like "it's broken" rather than "here is a bug":

- **Dragging a window to a desktop did nothing.** GTK only starts a drag if the widget was registered as a drag source before the handler that takes the button press. The order was the other way round, so the press handler won every time and a drag never began. The fix was swapping two lines.
- **Every Finder window was labelled "Bulk Rename".** Labels come from each app's `.desktop` file, so a window says "Calculator", not `gnome-calculator`. But Thunar's bulk-rename tool is also started as `thunar`, and its entry matched first. Skipping entries marked hidden fixed it.

## Launchpad is two windows

macOS's Launchpad closes when you click anywhere outside the icons. rofi has `-click-to-exit`, but it only fires on clicks outside rofi's window, and a full-screen window has no outside.

So `bin/launchpad` is 52 lines that open two windows:

1. A small GTK window behind, full screen, showing the wallpaper blurred and darkened (made once per wallpaper and screen size with ImageMagick, then cached).
2. rofi in front, as a centred box 86% by 88% of the screen, whose background is the matching slice of that same picture.

The two line up, so it looks like one surface. A click outside the box lands on the back window and closes both. Launchpad lists the same apps as Mint's own menu, so nothing goes missing in the move.

![Launchpad in dark mode: a search field at the top and a grid of app icons with their names on a blurred, darkened wallpaper.](/images/blog/mintosh-launchpad.jpg)

Then a nastier find. Press Return when nothing matches, and rofi runs whatever was typed as a shell command. Type "settings manager", press Return, and you get a full-screen *Failed to execute: 'settings manager'*. That's the friendly outcome; the real problem is that typed text gets run at all. Spotlight and Launchpad now hand rofi `bin/open-app`, 15 lines. It starts a command only if that program is what some installed app's `.desktop` file launches. Anything else does nothing, which is also what a Mac does.

## Three ways Xfce kept showing yesterday's appearance

`appearance light|dark|auto`, or Apple menu → Appearance…, switches everything with two looks:

- the theme, icons and window borders;
- the menu bar's text colour and the Apple logo;
- the dock, Spotlight, Launchpad, Mission Control and notifications;
- the wallpaper set;
- apps that follow the system colour scheme.

Auto is light from 7:00 to 19:00. It's 185 lines of shell, and each of these failures looked like the switch hadn't happened:

| Symptom | Cause | Fix |
|---|---|---|
| Plain ✕ □ – buttons instead of red, yellow and green | The first run set the theme name a few seconds before the theme was installed; Xfce only reloads a theme when its *name* changes | Forced runs set Xfce's default theme for a second first |
| Black menu-bar text on a dark wallpaper | The panel reads its stylesheet and the Apple logo only when it starts | Restart the panel after switching |
| No blur, no rounded corners, no shadows | picom 10 couldn't work out the type of one window rule (`_GTK_FRAME_EXTENTS@`), printed an error nobody saw, and exited | Two characters: `@:c` |

The third one went unnoticed longest, because Xfce's own compositor took over and looked *almost* right.

## A crash in the global menu, fixed at the source

On the real Air, moving a Chrome window to another desktop popped up Xfce's "plugin unexpectedly left the panel". The core dump pointed into `libappmenu-xfce.so`, the global menu. That's `xfce4-appmenu-plugin` 0.7.6, the version Ubuntu 24.04 and therefore Mint 22 ship. With Ubuntu's debug symbols (`xfce4-appmenu-plugin-dbgsym` from ddebs.ubuntu.com), the crash resolved to `get_layout_cb` in `dbusmenu-importer/model.c`:

```c
static void get_layout_cb(GObject *source_object, GAsyncResult *res, gpointer user_data)
{
	if (!DBUS_MENU_IS_MODEL(user_data))   /* reads user_data ...                       */
		return;
	DBusMenuModel *menu = DBUS_MENU_MODEL(user_data);
	...
	dbus_menu_xml_call_get_layout_finish(..., &error);
	if (error != NULL)                    /* ... before learning it was freed           */
		return;
```

When a window's menu goes away, the model is finalized, and finalizing cancels its pending D-Bus calls. The cancelled call's callback still runs, with `user_data` pointing at freed memory. The type check meant to guard against that dereferences it. The plugin's other async callbacks already finish the call first and return on `G_IO_ERROR_CANCELLED`; this one just had the two steps the wrong way round. The patch swaps them.

Script 4 now applies it, only when the installed package is exactly `0.7.6+dfsg1-4build4`. It downloads Ubuntu's own source tarball, applies the patch from the repo, and builds only the Xfce plugin with Meson. Then it installs the one library, records its checksum so a rerun skips the work, and removes the build tools it added. Ubuntu's packaging patches a duplicate in the translation list that the raw source still has, so the build skips the list: the installed package still provides the translations. A future update of the package simply replaces the rebuilt file.

## And one in the compositor, contained

picom 10.2, from the same releases, has its own failure. When a window is recreated (the panel restarting is the reliable trigger), it can hit an internal check, `!w->mask_image` in `win_bind_mask`, and abort. The glass then stays off until the next login. I didn't chase that one into picom. It now runs under `bin/glass`, nine lines that start it again if, and only if, it was aborted:

```sh
while :; do
  picom "$@"; rc=$?
  [ "$rc" -eq 134 ] || exit "$rc"   # 134 = aborted (SIGABRT); anything else is deliberate
  sleep 1
done
```

On the Air, three panel restarts in a row produced two aborts and no visible change.

## What's tested, and what isn't

mintosh is tested in an [OrbStack](https://orbstack.dev) machine running Mint 22.3 Xfce at the Air's 1366x768. `test/mintosh-test.py` uses xdotool to press keys and click, and Linux's accessibility tree to find buttons by name, wherever they've been drawn. It checks that:

- each shortcut reaches the mintosh helper it's bound to;
- Launchpad covers the screen, opens an app on one click, opens the best match on Return, runs nothing on Return with no match, and closes on Esc, on F4 again and on a click outside;
- Mission Control labels windows with their apps' names, adds and removes desktops, moves a window that's dragged onto a desktop, brings a clicked window to the front, and closes all three ways;
- each trackpad gesture's command does what it should.

It doesn't test Toshy or Touchegg. Both are well-tested upstream, and the first version of the test, which drove them through fake kernel input devices, mostly ended up testing the VM. OrbStack's machines only ever got the first two of those devices' nodes in `/dev/input`, so the third and fourth silently didn't exist. The test now presses the keys Toshy *sends* and runs the commands mintosh gives Touchegg, which is the part mintosh owns.

The other test is the Air, and the person who uses it.

## Try it

On any Linux Mint 22 Xfce machine, Mac or not, run scripts 3, 4 and 5 from the [README](https://github.com/isaacrowntree/mintosh#4-set-up-on-the-new-install). The hardware fixes switch on only when that hardware is present. Everything is English by default; a second language is opt-in (`LANG2=es_CO`, `KBD=es`). If you're moving someone off an old Mac, steps 1 and 2 back it up and sort their files from a second Mac before anything is wiped.

Issues and pull requests are welcome, especially from anyone with a 2014 or 2015 MacBook to try it on.
